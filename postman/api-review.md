# API payload and data-exposure review

Site: automationexercise.com. One row per endpoint. Observations come from my Postman and Newman runs.

| Endpoint | Params sent | Is every param needed? Why? | Response fields that look over-exposed | Your recommendation |
|---|---|---|---|---|
| GET /api/productsList | none | Yes. Nothing needs to be sent. | None that look sensitive. The catalogue is public product data (id, name, price, brand, category). The whole list is returned in one response, and one call took about 9.8 s in the Runner. | Add pagination or a limit so the full catalogue is not returned on every call. Return a real HTTP 405 for the wrong method instead of HTTP 200. |
| GET /api/brandsList | none | Yes. Nothing needs to be sent. | None. Brand data is public (id, brand). | Return a real HTTP 405 for the wrong method (PUT) instead of HTTP 200 with responseCode 405 in the body. |
| POST /api/searchProduct | search_product | Yes. It is the search term. | None that look sensitive. Results contain the same product fields as productsList. | Return HTTP 400 when search_product is missing. The API currently returns HTTP 200 with responseCode 400 in the body. |
| POST /api/createAccount | name, email, password, title, birth_date, birth_month, birth_year, firstname, lastname, company, address1, address2, country, zipcode, state, city, mobile_number (17 fields) | A request with a required field missing is rejected (HTTP 200, responseCode 400, and the message names the missing parameter). Even so, a login only needs name, email and password. Birth date, company, second address line and mobile number are not needed to create an account. | Response only has responseCode and message. However, re-using an email returns an "already exists" message, which confirms that an email is registered. Anyone can create accounts with no authentication or limit. | Require only name, email and password at registration and collect the rest later. Return HTTP 201 for success and HTTP 400 for errors. Use a generic message for duplicate emails and rate-limit account creation. |
| POST /api/verifyLogin | email, password | Yes. Both are needed to verify a login. | Response only has responseCode and message. | Return HTTP 404 or 401 for invalid details instead of HTTP 200 with responseCode 404 in the body. Return a token on success so later calls can be authenticated. |
| GET /api/getUserDetailByEmail | email (query parameter) | The email is needed to find the account, but no password or token is asked for, so anyone who knows an email address can call it. | The response returns the user's profile: id, name, email, title, birth_day, birth_month, birth_year, first_name, last_name, company, address1, address2, country, state, city, zipcode. The date of birth, home address and internal id are personal data that a caller looking up an email does not need. The password and mobile number are not returned. | Require authentication and let a user read only their own record. Return only the fields the caller needs (for example name and email). Do not return the date of birth, address or internal id. Return HTTP 404 for an unknown email. |
| PUT /api/updateAccount | name, email, password, title, birth_date and the other account fields sent as form data (the same set as createAccount), with the new name ({{userName2}}) and city ({{userCity2}}) | Not all of them. Email and password are needed to identify the account, and only the changed fields (name and city) are really needed. | Response only has responseCode ("200") and message ("User updated!"). Nothing over-exposed. | Accept a partial update with only the changed fields. Authenticate with a token instead of resending the password. Return HTTP 404 instead of HTTP 200 when the account is not found. |
| DELETE /api/deleteAccount | email, password | Yes. Both are needed to confirm who is deleting the account. | Response only has responseCode and message. A wrong password returns "Account not found!", which does not reveal whether the email exists. | Authenticate with a token, not a re-sent password. Return a real HTTP error status for failures instead of HTTP 200. |

## Notes
- Every negative request returned HTTP 200 and put the real error in the body responseCode (405, 400 or 404). This is a bug in the API, not in the tests.
- The not-found messages are inconsistent: "User not found!", "Account not found with this email, try another email!" and "Account not found!".
- Content-Type is text/html; charset=utf-8 even though the body is JSON.
- Response times varied from about 364 ms to 2.9 s in the first Newman run, and one productsList call took about 9.8 s in the Collection Runner.
- Error messages are descriptive and name the missing parameter, for example "... is missing in POST request".
